## 技術

### うまくいったこと

- **AIに本文を書かせない設計**：AIは根拠FAQのIDと確信度を返すだけにし、返信は承認済みFAQの原文とメニュー表から組み立てた。言い換え15件はすべてFAQの原文どおりで、料金の変更も次の質問から反映された。
- **規則とAIの二段構え**：予約希望・健康に関わる言葉は、AIを呼ばずに引き継ぐ。「かぶれ」の質問はAI呼び出し0回、返信まで1.20秒だった。
- **受信の永続化と排他**：受信を保存してから即時に受付を返し、処理権・通知の処理権を取ることで、本番の通知の記録9件は、いずれも引き継ぎ1件につき1回だった。
- **関数のリージョン**：Supabase（シドニー）に合わせて `syd1` に移し、返信完了は9.3秒（米国、AIなし）から4.48秒（AIあり）になった。

### つまずいたこと・学んだこと

- **組み合わせFAQの引き継ぎ**：旧FAQが「オーナーが確認してご案内します」という個別確認を約束する文面だったため、一般的な質問でも引き継ぎになったと考えられる（AIの判断内容は記録していないため、原因は特定できていない）。FAQの文面とAIへの指示を直して解消した。→ AIの判断理由（確信度・選んだFAQ）を、個人情報を含まない形で記録しておけば、原因を特定できた。
- **Vercelのリージョン設定**：管理画面の設定と再デプロイでは反映されず、`vercel.json` の `regions` が必要だった。
- **Hobbyの制約**：Cronは1日1回まで。毎分の式はデプロイに失敗するため、日次に変え、失敗時の即時引き継ぎと受信時の拾い直しを追加した。
- **ログの検索**：SupabaseのログでEvent messageの「Like」検索は、`%` がないと完全一致になる。Pathnameの完全一致で検索して、Cronの実行を確認できた。
- **OneDrive上の開発**：`.next` が読み取り専用になり、ビルドがEPERMで失敗することがあった（`.next` を消して再ビルドで解消）。

- 操作する画面やボタン名を先に確認し、手順を1つずつ進める。
